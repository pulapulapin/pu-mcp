# PuKnowledge 产品价值与使用场景

## 产品定位

PuKnowledge 是面向长期 AI 项目的本地可追溯工作台。它不替代模型、聊天窗口、正文文件或项目仓库，而是在这些入口之间维护一份可以核对的项目状态：当前任务是什么、依据来自哪里、采用哪个版本、哪些内容已批准、哪些仍是候选。

它最适合持续数周或数月、需要多次换会话或换 Agent、并且不能接受项目事实被静默改写的工作。

## 谁可能从中获得价值

- 同时维护多个长期研究课题的研究者、顾问和分析人员。
- 需要管理人物、时间线、章节、大纲及多个版本的长篇作者。
- 需要保留需求决策、技术方案、证据和变更原因的产品及工程团队。
- 在 ChatGPT、Codex、Claude Code、Cursor 等多个 Agent 入口之间切换的个人用户。
- 希望项目数据留在本机，并明确限制 Agent 可读目录的用户。

如果任务只持续一个会话、不需要核对来源、也不关心版本和回滚，PuKnowledge 可能会增加不必要的管理成本。

## 场景一：换 Chat 后继续长期项目

### 没有工作台时

用户把几周的背景重新粘贴进新会话。模型能复述一部分内容，但无法可靠判断哪条指令最新、哪些决定已经被推翻，也可能根据记忆补全不存在的事实。

### 使用 PuKnowledge

1. 用户明确选择项目。
2. Agent 读取当前任务、阶段、下一步和准确的会话快照版本。
3. 恢复接口返回 `READY`、`PARTIAL` 或 `BLOCKED`，并列出缺失来源。
4. Agent 只在已经交付的上下文范围内工作，不把“未读取”解释成“不存在”。

### 可验证的收益

- 减少重复解释项目背景的时间。
- 避免旧检查点覆盖当前方向。
- 可以指出本次恢复了什么、尚未恢复什么。

PuKnowledge 不能恢复宿主未保存的完整聊天，也不能证明一段摘要等同于原始对话。

## 场景二：有证据的长期研究

### 没有工作台时

研究结论散落在聊天、网页、PDF 和笔记中。几周后很难回答某个判断来自哪份资料、引用的是哪个版本，或者新资料是否已经推翻旧结论。

### 使用 PuKnowledge

1. 把来源登记为带版本和指纹的记录。
2. 将事实、引用、分析判断和未决问题分开保存。
3. 新任务按明确来源恢复，而不是把整个资料库一次性塞入上下文。
4. 保存新结论前预览差异，并保留旧版本。

### 可验证的收益

- 关键结论能够回到具体来源和版本。
- 来源变化时，可以识别过期引用。
- “没有证据”和“尚未读取证据”不会被静默混同。

PuKnowledge 记录证据链，但不会自动证明来源真实、权威或结论正确。

## 场景三：长篇小说与连载

### 没有工作台时

人物设定、候选剧情、正式正文和作者临时想法容易混在一起。卷纲修改后，后续章节、伏笔、人物关系和知情范围可能留下矛盾。

### 使用 PuKnowledge

1. 正文和 Canon 继续由项目文件承担内容权威。
2. 数据库记录章节、人物、事件、关系、任务和候选故事图的版本状态。
3. 写某章前，只恢复当前章节真正需要的资料。
4. 修改大纲时预览可能受影响的章节和关系。
5. 连续性检查输出证据与疑点，不把文学判断伪装成程序事实。

### 可验证的收益

- 候选剧情不会仅因被讨论就升级为 Canon。
- 新会话能够找到当前创作位置和必要前情。
- 大纲变化可以形成待复核的影响清单。

PuKnowledge 不能保证人物鲜活、故事精彩或文笔优秀；这些仍需要作者和编辑判断。

## 场景四：产品与技术方案决策

### 没有工作台时

需求、评审意见、实验结果和最终决定分散在多个聊天中。后来的人只看见“现在怎么做”，却不知道为什么这样做，以及哪些替代方案已经被否决。

### 使用 PuKnowledge

1. 记录需求来源、当前目标和范围边界。
2. 将候选方案、批准决策、风险和验收证据分开。
3. 新 Agent 接手时恢复当前方向，而不是重新发明已经讨论过的方案。
4. 方案变化通过预览、版本和影响关系保留过程。

### 可验证的收益

- 减少重复讨论已经解决的问题。
- 保留决策理由和失败实验。
- 可以区分“设计已经批准”和“代码已经验证”。

## 场景五：跨 Agent 和跨环境使用

PuKnowledge 的核心数据位于 MCP 服务及用户指定的项目存储中，而不是某个模型的聊天记忆里。支持 MCP 的宿主可以连接同一套项目状态，但每个宿主仍需单独验收工具发现、授权、长响应和交互行为。

| 环境 | 接入方式 | 当前产品状态 |
| --- | --- | --- |
| 本地 ChatGPT/Codex 插件 | 本地插件启动 `stdio` | 开发运行版已有真实项目证据；公开发行包待复验 |
| Codex CLI/IDE | 本地 MCP 配置 | 协议可接入，待公开版黑盒验收 |
| Claude Code CLI 2.1.311 | 本地 MCP 命令 | 合成项目真实宿主闭环通过；使用第三方模型，不代表 Anthropic 模型验收 |
| Cursor | `stdio` 或受保护的 HTTP | 合成项目真实宿主闭环通过 |
| TRAE | 本地 `stdio` MCP | 合成项目真实宿主闭环通过 |
| Kimi Code | 本地 `stdio` MCP | 因现有额度不足未执行，不计为失败 |
| VS Code Agent 模式 | 本地命令或远程 URL | 协议可接入，待黑盒验收 |
| 自建小说/研究工作台 | MCP/API 加独立 UI | 需要前端产品开发 |
| 定时或 CI 检查 | 命令行或程序化客户端 | 适合只读检查，尚无正式自动化产品 |
| 多人云服务 | 远程 HTTP | 缺少多租户鉴权和运营能力，不可直接开放 |

## 与相邻方案的区别

### 与聊天记忆的区别

聊天记忆由宿主决定保存和召回什么；PuKnowledge 要求显式项目、来源、版本和状态，并允许用户核对恢复结果。

### 与普通文件夹的区别

文件夹保存内容本身，但通常不表达当前任务、来源指纹、候选与批准边界、记录关系和保存冲突。PuKnowledge 不替代文件，而是管理 Agent 如何可靠地使用这些文件。

### 与通用 RAG 的区别

RAG 主要解决“找到相似内容”。PuKnowledge 更关注“当前任务应使用哪个准确版本、该内容具有什么权威状态、是否完整交付，以及写入是否经过预览”。两者可以组合。

## 销售前应如何证明价值

产品价值不能只由作者自己的项目证明。公开测试应使用不含私人资料的合成项目，并邀请未参与开发的用户完成相同任务。

建议至少验证以下指标：

| 指标 | 建议门槛 |
| --- | ---: |
| 新用户独立完成安装 | 至少 4/5 人 |
| 从安装到首次成功恢复项目 | 不超过 15 分钟 |
| 跨会话恢复当前任务的正确率 | 100% |
| 候选内容误标为批准事实 | 0 次 |
| 跨项目私有内容混入 | 0 次 |
| 关键结论可回到准确来源版本 | 100% |
| 相比手工粘贴背景所节省的时间 | 至少 30% |
| 测试结束后愿意继续使用 | 至少 3/5 人 |

同一个合成项目应在多个宿主中执行：发现项目、恢复任务、读取来源、预览修改、保存新版本、重新开会话恢复、检查项目隔离。只有协议连通而没有完成行为验收，不算产品通过。

仓库内的 `puknowledge-compat` 可以在目标宿主暂不可用时先排除服务端协议、工具缓存、响应预算和隔离方面的基础问题。它不是宿主模拟 UI，也不模拟模型会不会正确选择工具；报告中的 `real_host_verified=false` 是固定边界。详见[宿主兼容验证](HOST-COMPATIBILITY.md)。

外部测试者可以用 `puknowledge-compat --prepare-host <新目录>` 生成不含私人内容的持久验收夹具，再按[外部用户首装验收](EXTERNAL-USER-ACCEPTANCE.md)完成真实宿主测试。维护者本机重复执行该流程不能替代独立用户样本。

## 明确边界

- 默认面向单用户、受信任的本地工作区，不是现成的多租户服务。
- `READY` 表示所选来源已经按约定交付，不代表资料完整、结论正确或文学质量合格。
- Prompt 是任务指导数据，不能覆盖系统约束、工具授权、批准的 Canon 或 Owner 决策。
- 项目文件仍是正文和正式资料的内容权威；数据库负责版本、关系、任务状态和检索辅助。
- 未经授权，不自动采集资料、写入项目文件、修改 Canon 或启动后台流程。
